# ALAB Resident Database Design

## Goal

Create a version-controlled PostgreSQL schema for the ALAB resident workflows and apply it to the existing `alab-fire-responses` Railway PostgreSQL service. This increment creates data storage only; it does not yet submit the current forms, authenticate users, upload files, or alter resident screens.

## Approach

Use Prisma migrations as the schema source of truth. This keeps the database structure in the repository, allows reliable deployment with `prisma migrate deploy`, and gives the Next.js application typed models for the later API and authentication increment.

The alternative of executing ad-hoc Railway Dashboard SQL is excluded because it would leave the repository unable to recreate or review the schema. Raw SQL-only migrations are also excluded because Prisma is a better fit for the existing TypeScript application and planned server-side data access.

## Data Model

### Location reference data

- `municipalities`: `id`, `name`, `province`, `created_at`, `updated_at`.
- `barangays`: `id`, `municipality_id`, `name`, `created_at`, `updated_at`.

`municipalities.name` is unique within Antique. `barangays` is unique per municipality. The existing Antique municipality and barangay data will seed these tables, so resident addresses and incident locations use foreign keys rather than free-text locality names.

### Resident account and profile

- `users`: `id`, `email`, `username`, `password_hash`, `phone`, `role`, `account_status`, `terms_accepted_at`, `created_at`, `updated_at`, `last_login_at`.
- `resident_profiles`: `id`, `user_id`, `first_name`, `last_name`, `created_at`, `updated_at`.
- `resident_addresses`: `id`, `resident_profile_id`, `municipality_id`, `barangay_id`, `province`, `sitio_or_purok`, `complete_address`, `nearby_landmark`, `is_primary`, `created_at`, `updated_at`.

All current resident accounts have `role = RESIDENT`. Email, username, and phone are individually unique. `resident_profiles.user_id` is unique, ensuring one resident profile per user. A resident may have multiple addresses in the future, while registration initially creates one primary address.

Passwords are never stored in plain text: only a secure `password_hash` is retained. The confirmation-password field is never persisted.

### Identity verification

- `resident_verifications`: `id`, `resident_profile_id`, `front_document_key`, `back_document_key`, `selfie_key`, `status`, `reviewed_by_user_id`, `reviewed_at`, `rejection_reason`, `created_at`, `updated_at`.

The document fields hold private object-storage keys or URLs, not file bytes. Verification status is `PENDING`, `VERIFIED`, or `REJECTED`. Identity documents and selfies require restricted access and must never be delivered from a public bucket.

### Resident fire reports

- `fire_reports`: `id`, `reference_number`, `resident_profile_id`, `reporter_name_snapshot`, `reporter_phone_snapshot`, `fire_type`, `description`, `status`, `latitude`, `longitude`, `location_accuracy_meters`, `location_method`, `location_quality`, `is_within_antique`, `municipality_id`, `barangay_id`, `address_label`, `nearest_landmark`, `submitted_at`, `updated_at`.
- `fire_report_photos`: `id`, `fire_report_id`, `storage_key`, `original_file_name`, `mime_type`, `file_size_bytes`, `captured_at`, `uploaded_at`.

`reference_number` is unique and will be generated by server-side report-submission logic in the next increment. Fire types are `HOUSE_BUILDING`, `GRASS`, `FOREST`, `VEHICLE`, and `OTHER`. Report status initially supports `SUBMITTED`, `UNDER_VERIFICATION`, `CONFIRMED`, `REJECTED`, `FALSE_REPORT`, `DUPLICATE`, `NEEDS_MORE_INFO`, and `CLOSED`.

The report stores the location required by the resident report screen: latitude, longitude, GPS accuracy, GPS/manual-pin method, calculated quality, Antique validation, municipality, barangay, display address, and landmark. The system stores the active incident location only; it does not persist continuous resident location history.

Report name and phone are snapshots, preserving what BFP personnel used during verification even if the resident later edits their profile.

### Resident notifications

- `notification_preferences`: `id`, `resident_profile_id`, `push_enabled`, `incident_updates_enabled`, `emergency_alerts_enabled`, `guide_updates_enabled`, `created_at`, `updated_at`.
- `notifications`: `id`, `resident_profile_id`, `fire_report_id`, `type`, `title`, `message`, `read_at`, `created_at`.

One preference row exists per resident. A notification can optionally reference the related fire report.

## Relationships and Integrity

```text
users -> resident_profiles -> resident_addresses
                         -> resident_verifications
                         -> fire_reports -> fire_report_photos
                         -> notification_preferences
                         -> notifications
fire_reports -> municipalities / barangays
resident_addresses -> municipalities / barangays
```

Reports are retained as operational records; the system deactivates an account rather than deleting a resident who has submitted reports. Profile-side children can cascade on an unused profile, but an existing report prevents destructive resident removal.

Indexes will support the operational resident flows: `fire_reports(reference_number)`, `fire_reports(resident_profile_id, submitted_at)`, `fire_reports(status, submitted_at)`, and `fire_reports(municipality_id, submitted_at)`. The location columns are stored as numeric latitude/longitude for this initial increment; a PostGIS geometry index is deferred until the municipal GIS queries require it.

## Migration and Deployment

1. Add Prisma and its PostgreSQL runtime dependencies to the nested Next.js application.
2. Add the Prisma schema, generated client setup, migration scripts, and an idempotent Antique locality seed script.
3. Generate and validate the initial migration locally without exposing a database URL.
4. Use the Railway CLI to link the existing project/service, run the migration against its private `DATABASE_URL`, and run the seed command.
5. Verify the deployed schema through a non-sensitive database health check and table/seed checks only; credentials and connection strings will not be logged or committed.

## Error Handling and Security

- Railway migration failures stop deployment and leave the existing schema intact through transactional PostgreSQL migrations.
- The app does not expose `DATABASE_URL` to the browser or return it from an API route.
- File upload validation and storage integration are explicitly deferred; the schema only reserves protected object references.
- The later registration and report APIs must validate enum values, Philippine phone formatting, the Antique municipality/barangay relationship, and GPS bounds server-side.

## Verification

- Prisma schema validation and client generation pass.
- The migration applies successfully to Railway and is recorded in `_prisma_migrations`.
- All municipalities and barangays from the existing application list are seeded once, without duplicates.
- The existing test suite, lint, and production build still pass.

## Out of Scope

- Login, password hashing implementation, sessions, and role enforcement.
- Wiring sign-up, profile, report, upload, or notification interfaces to the database.
- Object storage bucket provisioning and document/photo upload APIs.
- Municipal BFP, provincial BFP, firefighter, dispatch, vehicle, and water-source database modules.
