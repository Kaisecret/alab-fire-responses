# Cross-Role In-App Notifications Design

**Date:** 2026-08-21  
**Status:** Approved design, awaiting specification review  
**Scope:** Resident, Municipal BFP, and Provincial BFP portals

## Goal

Replace hardcoded notification badges and sample notification records with one connected, secure in-app notification system. Residents, Municipal BFP personnel, and Provincial BFP personnel receive short, actionable updates generated by real application events.

This phase is in-app only. It does not send SMS, email, or browser push notifications.

## Current Problems

- Resident bell badges are hardcoded and the bell has no working notification surface.
- Municipal BFP has a static sample notification page and hardcoded unread counts.
- Provincial BFP links its bell to incidents and uses a hardcoded count instead of notifications.
- The existing `notifications` table supports resident profiles only.
- Notification controls and visual treatment are inconsistent across portals.

## Chosen Approach

Create a central account notification table used by all three roles, then expose it through role-specific server APIs. Role-specific routes are required because Resident, Municipal BFP, and Provincial BFP use different custom session cookies and multiple BFP roles may be signed in within the same browser.

The existing resident-only `notifications` table remains intact for migration safety. New events use `account_notifications`.

## Notification Data Model

Create `public.account_notifications` with:

- `id uuid primary key`
- `recipient_user_id uuid not null` referencing `public.users(id)`
- `actor_user_id uuid null` referencing `public.users(id)`
- `event_type text not null` constrained to supported notification events
- `category text not null` constrained to `INCIDENT`, `APPLICATION`, `RESPONSE`, `ACCOUNT`, or `SYSTEM`
- `title text not null` limited to 120 characters
- `summary text not null` limited to 240 characters
- `action_href text null` limited to 300 characters
- `entity_type text null`
- `entity_id uuid null`
- `context jsonb not null default '{}'::jsonb`
- `dedupe_key text null`
- `read_at timestamptz null`
- `created_at timestamptz not null default now()`

Indexes:

- `(recipient_user_id, created_at desc)` for the notification feed
- partial unread index on `(recipient_user_id, created_at desc) where read_at is null`
- partial unique index on `(recipient_user_id, dedupe_key) where dedupe_key is not null`

Row-level security is enabled. The application continues using server-side PostgreSQL queries and custom signed sessions, so no `anon` or `authenticated` Data API grants are added.

Notification content must stay minimal. Phone numbers, identity images, exact private addresses, and other protected resident data are never copied into notification rows. The notification links to an authorized page that loads protected details separately.

## Connected Event Flow

| Source event | Notification recipient | Card action |
|---|---|---|
| Resident submits a fire report | Active Municipal BFP accounts assigned to the detected municipality | Open municipal incident |
| Resident submits a fire report | Active Provincial BFP accounts | Open provincial incident view |
| Municipal BFP starts responding | Reporting resident | Open resident report details |
| Municipal BFP starts responding | Active Provincial BFP accounts | Open provincial incident view |
| Resident submits or resubmits an application | Active Municipal BFP accounts assigned to the application municipality | Open resident application |
| Municipal BFP approves an application | Applicant resident | Open application status |
| Municipal BFP requests corrections | Applicant resident | Open correction and resubmission form |
| Provincial BFP creates a municipal account | Created Municipal BFP user | Open profile or password-change screen |

Notifications are created only after the related database operation succeeds. When the related operation already uses a database transaction, its notification rows are inserted within the same transaction. Dedupe keys prevent accidental duplicate cards during request retries.

## Server Architecture

### Shared notification service

A server-only notification module owns:

- validated event creation
- recipient lookup by municipality or role
- paginated feed queries
- unread counts
- marking one notification as read
- marking all notifications as read
- server-generated, allowlisted action paths

### Role-specific APIs

Each portal uses endpoints that resolve only its own session cookie:

- `/api/resident/notifications`
- `/api/municipal-bfp/notifications`
- `/api/provincial-bfp/notifications`

Each endpoint supports:

- `GET` for the latest paginated notifications and unread count
- `PATCH` with a notification ID to mark one owned notification as read
- `PATCH` with `markAll: true` to mark all owned notifications as read

Requests cannot choose another user ID. The server derives `recipient_user_id` from the signed session. Municipal access also validates the active municipality assignment.

## Refresh Behavior

A shared client hook fetches notifications immediately, then every five seconds while the browser tab is visible. Polling pauses when the tab is hidden and resumes with an immediate refresh when visibility returns.

Mark-read actions update the interface optimistically and restore the previous state if the server rejects the request. A manual refresh remains available on full notification pages.

## Shared UI Design

### Visual thesis

A calm emergency operations feed using the established Resident Reports card language: clear icons, short utility copy, restrained red accents, and consistent spacing.

### Bell and unread badge

- One shared accessible bell component is mounted in all persistent portal layouts.
- The badge shows the real unread count and displays `99+` above 99.
- The badge is hidden when the count is zero.
- The button exposes expanded state and supports keyboard interaction.

### Quick notification panel

- Desktop opens a compact panel anchored beside the bell.
- Mobile opens a bottom sheet sized for touch interaction and safe-area spacing.
- The panel shows up to five recent notifications, a `Mark all read` action, and a `View all` link.
- Clicking outside, pressing Escape, or selecting a notification closes the panel.

### Notification cards

Cards match the Resident Reports visual system:

- 8px vertical gap between cards
- rounded white surface with a thin neutral border
- subtle red tint and unread dot for unread items
- category-specific icon inside a compact tinted icon tile
- short title
- one short context line
- small status badge when useful
- relative time
- chevron indicating the connected action

No notification uses long explanatory paragraphs. Examples include `New fire report`, `BFP is responding`, `Application approved`, and `Changes requested`.

### Full notification pages

Create or update:

- `/resident/notifications`
- `/municipal-bfp/notifications`
- `/provincial-bfp/notifications`

Each page contains:

- compact page title and unread total
- filters for `All`, `Unread`, `Incidents`, and `Applications`
- notification cards using the shared component
- empty, loading, retry, and end-of-list states
- manual refresh and mark-all-read controls

Portal accents follow the established themes, while layout, spacing, typography, and interaction remain identical.

## Error and Empty States

- A failed feed request keeps the last successful notifications visible and shows a compact retry state.
- A failed mark-read request restores the unread state and count.
- An empty feed shows one quiet bell illustration and the text `No notifications yet`.
- Invalid or no-longer-available action targets keep the notification readable and show `This item is no longer available` rather than navigating to an error page.
- Notification payloads are validated before a write transaction begins. Notification inserts then join the related transaction so the system cannot save a connected event without its required notification; unexpected database failures return a controlled error and log the event reference.

## Accessibility

- Bell controls have descriptive accessible names containing the unread count.
- Panels use dialog semantics on mobile and menu-like navigation semantics on desktop.
- Focus moves into the opened panel and returns to the bell when closed.
- Unread state is communicated through text and semantics, not color alone.
- Touch targets are at least 44px and status colors preserve readable contrast.
- Reduced-motion preferences disable panel and card entrance transitions.

## Verification

Automated tests cover:

- migration constraints, indexes, and RLS enablement
- session-derived ownership for every role API
- municipality-scoped Municipal BFP recipients
- province-wide Provincial BFP recipients
- resident-only access to resident notifications
- event creation for reports, responses, applications, reviews, and account provisioning
- deduplication during retried writes
- real unread counts and mark-read behavior
- five-second visible-tab refresh behavior
- shared bell and card UI integration in all three layouts
- removal of hardcoded badges and Municipal sample notifications
- TypeScript compilation and production build

## Out of Scope

- SMS, email, and browser push delivery
- notification sounds
- user-configurable category preferences for BFP accounts
- bulk notification broadcasting tools
- automatic deletion or archival policies
